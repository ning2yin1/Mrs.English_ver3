# 初回設定の遅延調査

## コミット比較と確認した処理

- 位置調整直前 `4dc47ab` → 位置調整 `5ee8730` は `src/result/animation.js` の2行だけ。共有CSS、初期化、設定、画像、SW、ビルド処理の変更はない。
- 次の `f1f6a00` も実行時の変更はリザルト専用3ファイル。QA画像・テストは公開用distへ含めない。
- リザルトのJSはモジュールとして読み込むが、`animateResult` は完了画面を描画したときだけ実行する。リザルトCSS・フォントは `loadPlayResources()` の呼び出し時だけ読み込む。初回設定でリザルトのRAFは開始しない。
- ニックネーム確定は `show('member')` へ進み、その画面のフォント読み込みと背景decodeを待つ。背景選択は既存の22枚の原画像をimgで取得する。これらは位置調整前後で同一。
- ビルドは素材・コードの内容ハッシュをSWのキャッシュ名に使うため、位置調整2行でも新しいキャッシュを作る。
- SWはインストール時に `cache.addAll` で440項目、91,587,641バイトを一括取得していた。公開更新で再取得が発生し、前景のフォント・画像と競合することを制限回線で再現した。

## 最小限の修正

`public/sw.js` の一括取得を低優先度・最大2並列へ変更。画像や取得対象を減らさず、全素材の取得が成功してからactivateする既存方針は維持。画面・保存機構は変更しない。

## 比較測定

`npm run build:pages` 後、`npm run test:setup-performance` で実施。ブラウザーは毎回新しいコンテキストを使用。ローカルHTTPで最大6接続、各リクエスト25ms＋256KiB/秒を設定する。GitHub Pages・実機の絶対時間を再現するものではない。

`pre` は位置調整前のリザルトJS、`before` は位置調整後のリザルトJSを使用し、いずれも従来SWを使用。その他の起動・設定コードは同一。`after` は今回のSWを使用する。

| 条件 | ニックネームOK→推し選択表示 | 背景選択表示→22枚ロード・decode完了 |
| --- | ---: | ---: |
| 位置調整直前（1回） | 5.590秒 | 2.377秒 |
| 位置調整後・従来SW（2回平均） | 5.685秒 | 2.837秒 |
| 今回修正後（2回平均） | 4.839秒 | 0.392秒 |

個別結果は `results.json`。位置の数値変更そのものによる遅延は確認できない。一括キャッシュ取得による競合は実験で確認できたが、ユーザーのiPhoneで観測した症状が同じ原因だけで発生したかは未確認。推し選択画面のフォント取得・写真decode自体の待ち時間は残る。推測による画質低下や大規模な読み込み変更は行っていない。
