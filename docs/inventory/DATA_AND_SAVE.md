# Collection連携・保存の契約

今回アプリ実装・GitHubアクセスはしていません。以下は既存の所持台帳を壊さず、個体別の強化・編成情報を追加するための契約です。現行の保存キーとAPIはCodexが実装時に既存コードから確認してください。

|領域|正とするデータ|扱い|
|---|---|---|
|所有・数量・初回入手日|既存Collectionの所持台帳|Inventoryもここを参照。別の所有台帳を新設しない|
|写真/枠/人物/レアリティ|既存Collection catalog|catalogIdを固定、元データを変更しない|
|個体levelとdeck|Inventoryの追加情報|所有台帳へ紐づくinstanceId別の情報として保存|
|Rコイン|既存アプリの残高保存/API|9979で初期化しない。画面ごとに別残高を作らない|
|初期設定/ニックネーム/背景|既存プロフィール|一切初期化・変更しない|

前回Collectionキットの保存契約候補は `mrsEnglishV3.collection.v1`（owned[catalogId].quantity / firstAcquiredAt）。これは現在の公開実装を今回確認した事実ではありません。実際のキー/APIが違えば既存へアダプターで合わせます。キーの推測書込みは禁止。

個体が既にあればそのinstanceIdを必ず再利用。まだ種類別quantityしかない場合は、既存数量を増減せず、既存catalogIdと序数から安定した個体IDを一度だけ対応付ける（例legacy:<catalogId>:0001）。再起動や並べ替えでIDを振り直さない。初回日時は所有台帳から参照し、個体強化で更新しない。

Inventory用サイドカーの構造例:

```json
{"version":1,"instances":{"legacy:motoki-r-01:0001":{"catalogId":"motoki-r-01","level":1}},"deck":["legacy:motoki-r-01:0001",null,null],"appliedDevGrants":{}}
```

キー候補はmrsEnglishV3.inventory.v1。実装時に未使用か確認する。サイドカーのinstancesは所有の別コピーではなく、既存所有に対応する個体のlevel情報。所持判定は常に既存台帳にjoinし、存在しない個体を表示/編成/強化できない。Collectionの集計と個体数が合わなければ既存データを保護して調整を確認する。所有数減少/未知catalog/未知フィールドを勝手に削除しない。

同じcatalogIdの別個体は編成可。同じinstanceIdを2枠以上へ入れることは不可。確定前と読込時にdeckの所有・3枠・重複を検証。破損deckは未編成として扱い、所有カードやレベルを消さず復旧可能にする。未知versionや不正JSONを空データで上書きしない。localStorage.clearは禁止。

強化時は最新level/残高を再読込→上限/費用/所有を再検証→残高減算とlevel+1をまとめて保存→成功後にUI更新。既存の保存APIにトランザクションがあればそれを使用。複数キーしかない場合は復旧記録/取引IDを使い、途中リロードでコインだけ減る状態と二重減算を防ぐ。操作中ロックと保存失敗時の復元を設け、別タブ更新がある値を古い画面で上書きしない。

正式Shopの付与は後日共通付与窓口を通し、同じ所有台帳と個体対応に追加する設計。今回はガチャ・パック演出・無料配布処理そのものを実装しない。今あるCollection UIや初回設定フローを変える理由にはしない。
