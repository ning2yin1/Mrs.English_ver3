# 購入・無料パック・保存・復旧

## 既存データを正とする

既存のカード管理、Rコイン管理、プロフィール/初期設定完了フラグ、Inventoryの個体ID・レベル・deckを最初に読み取り、そのAPIへ接続する。今回現行GitHubコードを確認していないので、保存キーを推測で確定しない。旧キットのmrsEnglishV3.collection.v1 / inventory.v1等は契約候補で、現行の実装が優先。プロフィールを初期化/再設定させない。別系統のwallet/所有データを新設して同期する方法は禁止。

レシートの構造はreceipt.schema.json。これは一度の購入の結果を保持する監査/復旧データであり、独立した常時所有台帳ではない。既存保存サービスにレシート/適用ID/表示進捗を追加する。互換性が必要な未知フィールドや古いレシートを勝手に削除しない。

## 確定操作

1. 購入確認を開いただけでは消費・抽選・付与しない。キャンセル/閉じるも同様。
2. 確定ボタンで1つのoperationId/purchaseIdを発行し、即座に画面内の確定操作をロック。同じ操作の二重タップ/再送は同じIDで扱う。
3. 最新の残高/設定完了/無料受取履歴/カタログを再読込。残高不足、負数/不正残高、無料受取済み/未設定、プール不備なら中止し何も減らさない。確認を開いたときの古い残高だけで判断しない。
4. 結果を1回だけ抽選し、catalogId、順序、rarity、level1、固定instanceId、購入日時、paidCost、無料claimEventIdをレシートへ準備。
5. 既存の永続化サービスで、残高差引、所有数加算、新規個体、無料受取フラグ（無料時だけ）、レシート/適用済みIDを一連のcommitとして保存する。
6. 成功が確認されてから開封画面へ。Collection/Inventoryは同じ保存データを再読込できる状態にする。演出完了を付与タイミングにしない。

通常10枚例は25000−10000=15000。無料は0消費で残高不変。ダイヤはどの場合も不変。本キットの数値を実残高として初期化しない。

## 原子性と中断の扱い

既存サービスにトランザクションがあれば最優先で再利用。IndexedDBを使用しているならwallet/ownership/instances/claim/receiptを同じDBの同じreadwrite transactionで更新する設計にする。既存保存の形式/所有者を勝手に置換しない。

localStorageは複数キーを原子的にまとめて更新できない。単にキーを順番にsetItemして安全だと扱わない。既存の複数キーを維持する場合は、共通保存サービスの排他/復旧バリアの下で以下のjournal方式を実装する。

|journal状態|意味と復帰|
|---|---|
|prepared|before/afterの値・revision、固定結果、IDを1つのjournal文字列に保存済み。既存キーはまだ変更しない。commit前に閉じた場合は購入未成立として安全に中止可能|
|committed|journalの単一書込をcommit点とし、以後固定結果を正として既存キーへ投影。途中再起動なら同じafterを適用し完了させる。再抽選/追加減算は不可|
|applied|全投影を確認済み。レシートを残し演出へ。表示進捗は付与状態とは別|

投影は「数をさらに加算する」処理を繰り返さず、IDで重複を排除するか、確認済みのbefore→afterを一度だけ適用する。現値がbeforeまたは期待afterのどちらでもなければ競合として停止し、他の新しい保存値を上書きしない。commit前の失敗は旧状態、commit後の一部失敗は同一journalから復旧する。未完了journalを消して新しい購入を許可しない。

このjournal方式は、関連する全ての読取/書込が共通保存サービスの復旧バリアを通る場合だけ成立する。古い別タブが直接walletを書き換える状況を安全にできると断言しない。利用可能ならWeb Locks等の実排他をfeature-detectして使い、既存側との協調を保証できない環境では購入を有効にしない/他タブを閉じて再開する導線を用意する。localStorage上の非原子的なleaseだけを完全な排他の代わりと扱わない。

保存サービスの最小統合は必要でも、既存TOP/Collection/Inventoryの見た目・配置・カード表示・編成処理は変更しない。接続口が無い場合は、既存画面を作り直さず必要な保存接続箇所を実装前に報告する。

## 付与の一意性

purchaseIdは取引を識別、各instanceIdはpurchaseId+indexで固定、appliedPurchaseIds/既存の同等機構で適用済みを判定。同じレシートを2回処理しても、コイン差引・個体追加・種類数量更新・無料消費は増えない。結果はimmutableで、UIの表示進捗とは切り離す。再起動時は最新pendingReceiptを確認し、appliedなら既存結果一覧へ復帰してよい。progressが壊れても安全な既定は結果一覧であり再購入ではない。

ストレージ容量不足/書込失敗/破損JSON/未知version/未解決catalogIdは既存データを保持して停止。localStorage.clear、カード削除、残高初期化、勝手な払戻し/再抽選をしない。commit済みだが画像だけ不足した場合はレシートを保持して原画像の再読込を案内する。

## 初回無料10枚と開発カード

正式eventId=mrs-english-welcome-10-v1。初期設定完了かつ正式のclaim未済のユーザーのみ対象。claim済みかどうかは正式の永続フラグ/既存の正式配布履歴で判定し、所有枚数では判定しない。無料も固定purchaseIdと通常10枚と同じ保証枠・演出・付与を使い、消費コインだけ0。

現在の開発用10枚は消去・初期化しない。release設定で開発seederだけを無効化し、すでに付与した個体とlevel/初回日/deckは保持する。開発grantIdを正式claimEventIdとして使わない。テスト10枚を持つユーザーでも正式無料パックが未受取なら別に10枚を1回受け取れる（例10→20枚）。2回目は増えない。

逆に既存の正式無料受取履歴がすでに存在すれば、その履歴を認識して再配布しない。古い履歴が不明なときにテストカード所持だけを理由に受取済み/未済を決めない。無料claimとカード追加も同じcommitに含め、途中終了や二重タップで二重受取できないようにする。
