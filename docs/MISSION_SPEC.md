# ミッション機能詳細仕様

## 1. 既存データとの接続

本制作で既存アプリのソースコードは調査していません。以下は実装上必要な意味と不変条件です。既存の関数名・保存キー・イベント名を決めつけず、Codexが調査して接続してください。ミッションのための第二の通貨残高・第二のカード台帳は作りません。

## 2. 判定する事実

|事実/確定点|対象|更新する内容|
|---|---|---|
|回答が初めて採点・保存された|D02、D03|正解なら正解数+1。実際の連続正解数を更新し最大値を保持。不正解で実連続値0|
|ステージの10問すべてが完了して保存された|D01、D04、D05、W01〜W04|クリア数+1。文法IDを集合に追加。難易度と全問正解を判定|
|カード強化の通貨消費とレベル更新が正常に保存された|W05|成功回数+1。確認ボタンや演出完了時では数えない|
|各更新後|D06、W06|その期間の先行5件の達成数を再計算|

1ステージは10問。クリアに最低正解数はなく、10問完了なら0問正解でもクリア数に数える。途中終了はステージクリア・文法クリア・パーフェクトに数えない。

D02/D03は回答時点の条件なので、回答を確定して獲得した進捗・ミッション報酬はその後途中終了しても取り消さない。ステージスコア/Rコインの途中終了時無報酬ルールとは別です。既存コードが回答単位の保存に対応しない場合は、独断で「クリア時だけ」に変更せず接続の不足を報告する。

「5コンボ」は同一ステージ内の実際の連続5問正解。ステージをまたいで足さない。カードのCOMBO SUPPORT等がスコア用コンボを保護しても、不正解が挟まった実正解連続数は0。スコア用コンボをD03の唯一の根拠にしない。

文法は表示名や一覧の位置でなく、既存の安定した文法IDで集合管理。難易度違いでも同じ文法は1種類。NORMAL以上はNORMAL/HARD。W02はHARDのみ。W04は正解数10かつ総問数10かつステージ完了。W05は強化失敗・コイン/ダイヤ不足・レベル上限・キャンセルでは増やさない。

## 3. 日本時間の期間

- デイリー：Asia/Tokyoの暦日。毎日00:00:00から翌日00:00:00の直前まで。
- ウィークリー：日本時間の月曜00:00:00から翌月曜00:00:00の直前まで。
- 日次キーはJSTのYYYY-MM-DD。週次キーはその週の月曜日の日付。ISO週番号のみは使わない。
- UTCや端末現地の曜日で判定しない。日本時間へ変換した暦日/曜日から求める。
- 日本時間2026-11-02(月)00:00はUTC2026-11-01(日)15:00。
- 起動、フォアグラウンド復帰、MISSION表示、進捗イベント処理の直前に期間を照合する。起動中は次境界へのタイマーを補助利用し、タイマーの発火だけを正本にしない。
- 0時更新で進捗と報酬済み状態だけを新期間へ切り替える。既存通貨・所持カード・育成・ガチャデータは保持。過去期間の台帳/処理済みIDを即削除して再送二重処理を招かない。

### 境界の扱い

各確定イベントの発生時刻で所属期間を決める。日付をまたぐステージは、回答正解は回答確定時のデイリー、ステージクリアは完了時のデイリー/ウィークリーへ。実連続正解列は同じステージなら境界で断ち切らず、5連続目の確定した期間でD03を評価する。

確定済みの再送イベントは元の期間キー・IDで再照合し、新期間へ二重算入しない。保存前にアプリを終了した操作は成功扱いにしない。過去に未記録のプレイを起動時に推測して付与しない。バックエンドや既存イベントジャーナルがある場合、未処理の正当な確定イベントは元期間へ適用し、報酬は同じ付与キーで一度だけ復旧する。

アプリを閉じて期間をまたいでも、次回復帰時に現在期間を表示。空白期間のミッションを自動達成・自動配布しない。端末時計しかない場合、時計改変の完全防止はできないため既存の時刻方針に合わせる。新しいオンライン必須条件を勝手に加えない。

## 4. 保存する意味（実際の構造は既存方式に合わせる）

- ユーザー識別、スキーマバージョン。
- 期間種別と期間キーごとの集計：ステージ数、正解数、実正解連続最大値、文法ID集合、NORMAL/HARDクリア数、HARD数、パーフェクト数、強化成功数。
- ステージ別の実連続正解数と直前の処理済み回答位置。D03再開判定に必要。
- 同じ事実を数えない安定ID：回答=ステージ個体ID+問題位置+最初の採点、クリア=ステージ個体ID、強化=その強化操作ID。同じ問題の別ステージでの正解は別事実。
- ミッション別の達成・報酬済み記録。付与キーは「ユーザー/機能バージョン/期間種別/期間キー/ミッションID」の組合せ。
- 未表示通知のoutbox情報と表示済み扱いのID。通知と通貨を結び付けて再付与しない。

保存方式は既存の正本を優先し、IDB/単一保存オブジェクト/サーバートランザクション等で必要な一貫性を満たす。複数の独立したlocalStorageキーを順番に書く方式で「完全な原子性」と称さない。既存方式が原子的更新できなければ、操作ジャーナルと復旧ルールを含めるか、既存保存設計の最小拡張を検討する。

## 5. 更新と自動報酬の一連処理

1. 対象ユーザー・期間を確定し、既存保存の排他/トランザクションを開始。
2. 元イベントIDが処理済みなら変更せず終了。
3. 日次と週次の対象カウンタ/集合を更新する。1イベントで両方更新可能。
4. D01〜D05/W01〜W05の達成を再評価。新達成かつ報酬キー未登録だけを付与候補へ。
5. 先行5件がすべて条件を満たしたら、同じ処理内でD06/W06を評価する。
6. 進捗、処理済みイベントID、報酬キー、既存Rコイン/ダイヤ残高、通知outboxを一貫した1回の確定更新として保存する。
7. 保存成功後、画面の完了状態と共通残高を再表示し、通知キューへ反映する。保存失敗時は付与済みの外観や成功通知を出さない。

リトライは同じイベントID/付与キーを使う。リロード、二重タップ、表示再描画、タブ切替、通知終了は新しい報酬トリガーではない。ロック前の古い残高を使わず、ロック内で最新値から計算する。複数タブ/同時処理も既存保存の排他に従う。

同時達成通知はデイリーD01→D06、次にウィークリーW01→W06の順に並べる。6件目は必ずその先行5件の通知より後。Rコインとダイヤは別残高で加算し、デイリー全達成5ダイヤに通常5件のRコインを重ねて再加算しない。

## 6. 初回導入・既存セーブ保護

ミッション用フィールドだけを欠損時に追加し、初期進捗0、未付与にする。既存カード、レベル、入手日、デッキ、Rコイン、ダイヤ、ログイン履歴、開発用カードは維持する。参照画像の値を保存しない。過去プレイの遡及加算は今回の依頼にないため行わない。導入後の確定イベントから集計する。既存ミッションが見つかった場合は別物を並列追加せず、ID/期間/付与履歴の移行方法を先に確認する。

破損/読込失敗を「新規ユーザー」として初期化しない。既存の復旧/バックアップ経路を優先し、残高やカードを消さない。保存のバージョン更新は移行を再実行しても結果が増えないようにする。
